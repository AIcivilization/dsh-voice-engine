# 讯飞 × DSH 语音能力结合方案

> 调研日期：2026-11-02
> 数据来源：讯飞开放平台官方文档、dsh-plugin-catalog（8489 条插件目录）、本机 dsh 0.2.x 插件源码

---

## 一、结论先行

**不要做第 106 个「朗读回复」插件。**

dsh 现有 105 个语音类插件，其中 63 个是 TTS 朗读、49 个是语音输入。这两块是红海：Edge TTS 免费、SenseVoice 本地免费，新插件没有任何立足点。

真正的空白在于：**没有任何一个插件把语音当成「生产资料」来生产**。
- 105 个语音插件里，用讯飞 ASR/TTS 的数量是 **0**
- 没有插件能输出「音频 + 时间轴 + 字幕」这套完整的配音交付物
- 没有插件把「改一句文案只重合成那一句」这种工程化能力做出来

所以定位应该是：**dsh 里的音频生产流水线**，而不是又一个语音按钮。核心卖点是 **配音 + 时间轴 + 字幕一体化**，这是讯飞 TTS 不提供、而 dsh 的 agent 能力（读写文件、跑 ffmpeg、批量处理、断点续传）恰好能补上的缺口。

## 二、讯飞能力底牌（已核实）

| 能力 | 接口 | 关键约束 | 对我们的意义 |
|---|---|---|---|
| 在线语音合成 | `wss://tts-api.xfyun.cn/v2/tts` | **单次 < 8000 字节（约 2000 汉字）**；官方目录 158 个发音人编码、121 个有免费样音（详见 6.7）；speed/pitch/volume/bgs | 基础产能 |
| 长文本合成 | online_tts_long | 万字级单次 | ⚠️ 整段出音频，**不给时间戳**，反而不适合做时间轴 |
| 超拟人合成 | smart-tts | 双向流式、副语言标签（拟声词/韵律）、多情感 | 高质量配音、情感旁白 |
| 一句话复刻 | quick_tts | 一句话克隆，24k 采样效果最佳，音频 ≤ 3M | 品牌音色、个人音色 |
| 高精度声音复刻 | 声音复刻 | 建议 3–10 分钟干音 | 商用级音色资产 |
| 语音听写 | iat（流式） | 实时流式 | 语音输入（红海，不做主攻） |
| 实时语音转写 | rtasr | 返回带时间戳的文字流 | 直播字幕 |
| 录音文件转写 | lfasr | **句级 bg/ed + 词级 wordBg/wordEd（10ms/帧）**；说话人分离（官方标注"测试效果，未达商用"）；角色分离；方言/小语种；热词 200 个；10 个垂直领域 pd；≤5 小时 / ≤500M | ⭐ 时间轴的核心武器 |
| 语音评测 | ise | 发音打分 | 语言学习、口播训练 |

**三个致命约束，必须在设计阶段就吃进去：**

1. **TTS 不返回时间戳。** 返回字段只有 `code / message / sid / data.audio / data.status / data.ced`。`ced` 是「已合成文本的字节数」，不是时间。想要时间轴，只能自己算。
2. **单次 2000 汉字上限。** 长文案必须切分，切分点必须保留原文偏移，否则字幕对不上。
3. **长文本接口（万字级）不给时间戳。** 这是个反直觉的坑——看起来省事，实际是死路。**必须逐句短文本合成**。

## 五、产品形态

一个插件 `dsh-xfyun`，两条主线：

```
dsh-xfyun
├── 主线 A：文本 → 音频 + 时间轴（配音）
│   ├── xfyun_dub        文案 → 音频文件 + SRT + manifest.json
│   ├── xfyun_tts        单段合成（调试/短句）
│   ├── xfyun_clone      声音复刻（一句话 / 高精度）
│   └── xfyun_voices     按场景/声线/语种/关键词查音色（喂给 agent）
│
├── 主线 B：音频 → 文本 + 时间轴（转写）
│   ├── xfyun_transcribe 音频/视频 → 逐字稿 + SRT（句级/词级）
│   └── xfyun_subtitle   视频 → 字幕文件（含翻译）
│
├── 页面层 ⭐ 已具备原型
│   ├── 音色页 /xfyun/voices   235 条音色池，筛选 + 试听 + 选中即带入配音
│   └── 配音台 /xfyun/dub      分段编辑 + 时间轴预览 + 三件套导出
│
└── 共享底座
    ├── timeline.js      时间轴引擎（本项目最核心的模块）
    ├── segment.js       文本切分（保留原文偏移）
    ├── cache.js         片段级缓存（增量重配的基础）
    ├── voices.json      235 条音色目录（内置数据，见 6.7）
    ├── xfyun-auth.js    双协议鉴权（WS 的 HMAC-SHA256 / HTTP 的 MD5→HMAC-SHA1）
    └── audio.js         PCM 拼接、静音插入、ffmpeg 转封装
```

**关键：`timeline.js` 是护城河。** 谁都能调 TTS，但只有把时间轴算准了，输出才能直接进剪辑软件。

## 六、技术方案（核心难点拆解）

### 6.1 时间轴怎么算 —— 这是全案最关键的一步

**设计决策：放弃长文本接口，改用「逐句短文本合成」。**

原因：长文本接口（万字级）返回整段音频、无时间戳，事后想切出句子边界只能靠 ASR 反推，误差和成本都高。而逐句合成天然带边界：

```
文本 → 按标点切句（每句 < 8000 字节）
     → 逐句调 v2/tts（PCM 16k/16bit/mono）
     → 每句音频字节数 ÷ (16000 × 2) = 该句精确时长（毫秒级，无误差）
     → 累加 + 插入句间停顿 → 得到每句 bg / ed
     → 拼接 PCM → 单次编码为 mp3/wav
```

**句级时间戳的精度是「零误差」**——因为时长是从音频数据本身算出来的，不是估算的。这比 ASR 反推靠谱得多。

### 6.2 词级时间戳的三档方案

| 档位 | 方法 | 精度 | 成本 | 适用 |
|---|---|---|---|---|
| 快（默认） | 句内按字符数加权分配（逗号 1.5×、句号 2× 权重） | ±150ms | 0 | 90% 的卡点字幕够用 |
| 准 | 整段音频送 lfasr，开 `has_participle=true` 拿 `wordBg/wordEd`（10ms/帧），与原文字符做序列对齐（编辑距离） | ±30ms | 转写费用 | 精细字幕、逐字高亮 |
| 巧 | 超拟人接口二进制模式的 `data.spell`（拼音序列）辅助对齐 | ±80ms | 0 | 折中方案 |

默认走「快」，提供 `--precise` 开关走「准」。不要默认上 lfasr——贵且慢。

### 6.3 增量重配（场景 3）

```
片段 key = sha256(文本 + 音色 + speed/pitch/volume + 接口版本)
```

- 每句独立缓存音频文件
- 文案改动 → 只有 key 变化的句子重新请求
- 时间轴整段重排（纯计算，毫秒级）
- 已合成片段直接复用，**改一句的成本 = 合成一句的成本**

这是把「配音」从一次性操作变成「可迭代工程」的关键。

### 6.4 讯飞协议适配的两个坑

1. **鉴权有两套**：WebSocket 类（TTS/iat/rtasr）用 `HMAC-SHA256` 拼签名 URL；HTTP 类（lfasr）用 `signa = Base64(HmacSHA1(MD5(appid+ts), secretkey))`。别混用。
2. **lfasr 是异步五步流程**：`prepare → upload（分片）→ merge → getProgress（轮询，仅 status=9 可取结果）→ getResult`。结果只存 30 天、最多取 100 次。必须做状态持久化，否则 agent 一重启就丢任务。

### 6.5 在 dsh 里的挂载方式（已核实源码）

```js
export const name = 'dsh-xfyun'
export const inject = ['tools', 'systemPrompt', 'webServer', 'webStartup']

export function apply(ctx) {
  // 1. agent 工具
  ctx.tools.register({ name: 'xfyun_dub', /* ... */ })

  // 2. 系统提示：告诉 agent 什么时候该用讯飞而不是免费方案
  ctx.systemPrompt.section({ /* 配音/字幕任务优先走 xfyun_* */ })

  // 3. HTTP 路由：试听、下载、任务进度
  ctx.effect(() => ctx.webServer.register({
    kind: 'prefix', path: '/xfyun', handler: handleApi
  }), 'dsh-xfyun: API routes')
}
```

`package.json` 里 `dsh.manifestVersion: "1"` + `dsh.bundle.patch` 指向 `cordis.patch.yml`，前端通过 `dsh.client.inject` 挂 React 组件。本机 `~/.dsh/profiles/web` 的 patch 层为空数组，直接 insert 即可。

**API Key 绝不下发到浏览器**——key 留在 host 侧，浏览器只发文本和参数（参考 dsh-voice-scribe 的做法）。

### 6.6 交付物格式

一次 `xfyun_dub` 应该产出三件套：

```
output/
├── narration.mp3        配音音频
├── narration.srt        字幕（句级/词级可选）
├── narration.ass        卡点样式字幕（可选）
└── manifest.json        每句：文本 / 音色 / bg / ed / 时长 / 缓存 key
```

`manifest.json` 是二次编辑的抓手：改稿时读它就知道哪句变了。

### 6.7 音色目录与试听台（已具备原型）

这是目前唯一**已经做出东西**的模块，应该成为产品的第一个门面。

**数据底座（2026-11-02 已整理完毕）**

| 来源 | 数量 | 有样音 | 有编码 | 说明 |
|---|---|---|---|---|
| www 产品页 | 121 | 117 | — | 聆X 情感系列 + 多语种 + 方言，CDN 静态 wav |
| 官方全量目录 `tts_language_list` | 158 | — | 158 | 权威清单，`x4_xxx` 编码可直接填 vcn |
| saas 角色音色 | 68 | 0 | — | 配音向角色，**无样音、点了就扣点** |
| 合并去重 | **235** | 114 | 158 | 三源只有 3 个重叠（聆小珊、聆小璇、聆飞哲） |

**⭐ 关键数字：编码 ∩ 样音 = 100 条。** 这 100 个是「既能免费听、又能直接拿来用」的黄金子集，产品默认只展示这批，其余明确标注「需控制台实测」——不要让用户在一个音色上试听半天，最后发现用不了。

> 注：初版算出的 97 是错的。漏掉的 3 个音色（如 `x4_lingxiaowan_boy`）名字带后缀（「聆小琬-小男孩」），按名称匹配时对不上试听台的「聆小琬」。改用**样音文件名反查**后补回，这也再次说明名称不能当主键。

编码前缀分布也说明了代际：`x4_` 80 个（新一代）、`x2_` 54 个（多语种）、`x3_` 5 个、`x_` 10 个（老版）、其他 9 个。

**产品化分三层，同一份数据服务三个对象**

```
voices.json (235 条)
   ├──→ 人：音色页（筛选、试听、选中）
   ├──→ agent：xfyun_voices 工具（按场景描述推荐候选 + 样音）
   └──→ 配置：vcn 编码直接写入 manifest，不用猜参数名
```

第三层最容易被忽略但价值最大：以前开发要翻文档猜 `x4_lingfeizhe_zl` 这种编码，现在 agent 查完直接填。

**两段式试听（核心产品巧思）**

现有试听台解决的是第一段，但有个真实痛点：静态样音是讯飞固定的演示文案，**听不出你的文案读起来是什么效果**（语速边界、长句断气、专业名词读音都测不出来）。

| 阶段 | 手段 | 成本 | 作用 |
|---|---|---|---|
| 第一段：粗筛 | 117 个静态样音，在线播放 | **0**（不登录、不扣点） | 从 121 砍到 5–8 个候选 |
| 第二段：验证 | 用自己的一句文案调 TTS 合成 | 1 次调用 | 确认真实效果，定稿 |

音色页上就该有个「用我的文案试」按钮——输入框默认带当前文案的第一句，点一下合成，1 秒出结果。这一步把「选音色」从看样片变成真实试音。

**技术实现要点**

- `voices.json` 内置到插件（235 行精简字段约 30 KB），拼音全拼 + 首字母索引已在数据里，前端纯本地匹配，零依赖零请求
- **前端重写成 React，不要用 iframe 包现有 HTML**——因为要跟配音表单联动（选中音色 → 直接带入 `xfyun_dub` 的 vcn 字段）。iframe 会把这个联动切断
- 现有 37 KB 单文件 HTML 保留作原型兜底，挂 `/xfyun/voices-legacy` 即可
- **样音防盗链风险**：现在是直接引 CDN 公开 wav。一旦讯飞加 Referer 白名单就会集体放不出。对策：首次播放成功后落盘缓存到 `~/.dsh/dsh-xfyun/audio/`，**按需缓存而不是打包 80 MB 进 npm 包**
- saas 那 68 个角色音色单独分组、明确标注「需控制台开通 + 消耗点数」，绝不和免费样音混排

### 6.8 数据校对（试听台目前是粗稿，进产品前必须修）

我拿试听台内联的 121 条数据与 235 行对照表做了逐条比对，发现 6 类问题：

| # | 问题 | 数量 | 严重度 | 能否自动修 |
|---|---|---|---|---|
| 1 | **别名不统一**：「讯飞潘婷」vs「潘婷」、「讯飞叶子」vs「叶子」 | 26 条 | 🔴 高 | ✅ 100% 可自动 |
| 2 | 名称带前导空格（`' 小师'`、`' 小忠'`、`' 帕蒂古里'`） | 3 条 | 🟡 中 | ✅ 可自动 |
| 3 | 同一音色重复条目 + 样音归属矛盾（聆小琬） | 1 组 | 🔴 高 | ❌ 需人工判断 |
| 4 | 分类口径不一致（「多语种场景」vs「通用场景」） | **55 条** | 🟡 中 | 需先定规则 |
| 5 | 声线粒度不一致（大类 vs 细分） | 34 条粒度差 + 1 条真冲突 | 🟢 低 | 需先定规则 |
| 6 | **拼音字段设计错误**：`p` 存的是「名称+风格+场景」全拼 | 121/121 | 🟡 中 | ✅ 可重算 |
| 7 | **名称带后缀导致漏匹配**（「聆小琬-小男孩」vs「聆小琬」） | 3 条 | 🔴 高 | ✅ 样音文件名反查 |

**第 1 条比看起来严重，而且它会掩盖其他问题。** 26 个音色在对照表里"查不到"，全部是因为试听台叫「讯飞潘婷」而对照表叫「潘婷」。这带来两个后果：

- 现有结论里「两边都有只有 3 个」是**错的**——真实重叠远不止 3 个，之前算出的统计偏差是别名造成的假象，不是两套产品线互不相干
- 修掉别名后重新统计，分类冲突从 33 条涨到 **55 条**。也就是说**别名一直在掩盖冲突**：匹配不上的直接跳过了，看不见的错才是最危险的

这条恰好证明了「用 code 做主键」不是洁癖，是必需的。

**第 3 条是真实数据错误。** 聆小琬在试听台出现两次：

| 声线 | 场景 | 分组 | 样音文件 |
|---|---|---|---|
| 可爱女童 | 通用场景 | 童声 | `聆小琬-小男孩.wav` |
| 助理女声 | 客服助理 | 女声 | `8-聆小琬-助理.wav` |

第一条标"可爱女童 / 童声"，样音文件却叫"小男孩"——声线与文件自相矛盾。对照表里聆小琬只有一条（成年女声 / 客服助理 / `x4_lingxiaowan_en`）。这组必须人工确认，不能自动合并。

**第 6 条会让搜索变成噪声源。** `p` 字段实际存的是 `lingfeizheqinqienanshengyuyinzhushou`（名称+风格+场景全拼），后果是搜 `yuyin` 会命中所有「语音助手」分类的音色，搜 `nvsheng` 会命中所有女声。拼音索引应该**只由名称生成**。

**样音链接本身没问题**：抽样 15 个地址全部 HTTP 200。问题都在元数据标注，不在数据源。

**根治办法：改用发音人编码做主键，不要用名称。**

名称是弱标识——会变、有别名、有前后空格、有「讯飞」前缀。编码是强标识。建议建规范表：

```
code (主键) → { 标准名, 别名[], 场景, 声线, 样音URL, 来源 }
```

流程：
1. 以官方 158 条目录为权威源，全部以 `code` 为主键入库
2. 试听台 121 条名称全部映射到 code，映射不上的挂「待确认」
3. 人工只处理映射失败 + 冲突项（预计 5–10 条），其余全自动
4. 拼音字段由标准名重算

**验收标准**（写进 CI 或校对脚本）：
- 每个音色有唯一 `code`
- 每个 `code` 至多一个样音 URL
- 名称无前后空格、无「讯飞」前缀（或统一保留，二选一）
- 分类 / 声线取值落在枚举内
- 拼音字段只由标准名生成

### 6.9 合并还是分开：合成一个页面，内部双视图

**结论：合并成一个页面，内部做「一表双视图」。不要维护两个页面。**

三个理由：

1. **它们是同一批实体的两个视图，不是两个功能。** 卡片视图重听觉（听），表格视图重信息（查编码、看可用性）。用户要的是随时切换，不是跳转。
2. **真实动线是「听 → 查 → 定」。** 先在卡片里听中一个，然后想知道这音色到底能不能用（有没有编码、要不要开通），再选定。分开就要来回切页，还得靠记忆对上名字——这就是「不直观」的根源，不是排版问题。
3. **两份数据必然再次跑偏。** 现在就已经跑偏了（6.8 那 6 类问题全是双份数据造成的）。一个数据源一个页面，才不会继续产生差异。

**信息架构**

```
音色页 /xfyun/voices
├── 顶部    统一搜索（中文 / 拼音 / 编码）+ 视图切换（卡片｜表格）
├── 筛选条  声线 · 场景 · 语种 · 可用性
│           可用性 = 能听能用 100 / 仅能听 17 / 仅能用 58 / 需开通 60
├── 主体
│   ├── 卡片视图  大播放键 + 名称 + 风格 + 编码角标 + 可用性徽标
│   └── 表格视图  名称 / 编码 / 声线 / 场景 / 样音 / 可用性 / 操作
└── 底部固定「已选」条  选中音色 → 编码 + 试听 → [带入配音]
```

**四个关键设计点**

1. **可用性徽标是页面的灵魂。** 🟢 能听能用（100）／🟡 仅能听（有样音无编码）／⚪ 仅能用（有编码无样音）／🔴 需控制台开通（saas 那 68 个）。这一列直接告诉用户下一步该干什么，比任何排版优化都有效。
2. **表格视图里也要有播放按钮**，不是只有卡片能听。反之卡片上也要显示编码。两个视图的信息互补，不是互斥。
3. **选中态跨视图共享**，底部「已选」条常驻，选中后一键带入配音表单的 vcn 字段。
4. **默认只展示 100 个黄金子集**，其余折叠在「显示全部 235 个」后面。

**什么时候分开也合理**：如果将来音色池涨到上千、且要面向「纯创作者」和「纯开发者」做两个完全不同入口，可以拆成「选音色」和「音色手册」。但现在 235 条，合并没有任何负担。

**两层落地**

| 阶段 | 做法 |
|---|---|
| 现在（独立 HTML） | 改造现有试听台：加视图切换 + 编码列 + 可用性筛选 + 修 6.8 的问题 |
| 插件内（React） | 同一路由两个视图，共用 `voices.json`，与配音表单联动 |

## 八、风险与成本

| 风险 | 说明 | 应对 |
|---|---|---|
| **费用** | 讯飞需实名 + 付费；新用户有 1 万次交互 / 50 小时转写免费额度（够开发期用） | 缓存复用降本；默认音色走免费额度 |
| **并发限制** | 各接口有 QPS 上限，长文本逐句合成会打满 | 内部队列 + 指数退避 + 可配并发数 |
| **声音复刻合规** ⚠️ | 克隆他人声音涉肖像权/声音权，国内已有判例 | 强制「我拥有该声音授权」勾选 + 水印/元数据标记 + README 显著声明 |
| **时间戳精度预期** | 词级是估算，用户可能误以为精确 | 输出时标注精度等级；精细场景引导开 `--precise` |
| **免费方案竞争** | Edge TTS 免费且够用 | 不打价格战，打「质量 + 交付物完整度」：情感、方言、复刻、字幕 |
| **官方能力变更** | 讯飞接口字段/限额可能调整 | 版本探测 + 降级到长文本接口（牺牲时间轴） |
